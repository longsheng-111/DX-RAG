## 3. 调优记录（压测暴露 → 修复 → 复测）

**发现**：S1 首轮 19.4% 连接重置、p95 高达 64s。定位为 `/api/query`、`/exam/start`、
`/exam/next` 三个 `async def` 处理器**直接在事件循环里执行同步阻塞代码**
（LLM 调用 + CPU 嵌入，单次秒级到数十秒），20 个并发请求被单事件循环串行化；
`/chat` 此前已有 `asyncio.to_thread` 包裹（routes.py 注释），这三个端点是漏网之鱼。

**修复**（`backend/app/api/routes.py`）：
- `/api/query`：`qa_query` 改经 `asyncio.to_thread` 执行（与 /chat 同款）
- `/exam/start`、`/exam/next`：处理器主体抽为同步函数 `_exam_start_impl` /
  `_exam_next_impl`，薄异步壳经 `asyncio.to_thread` 调用；逻辑零改动，
  重构后考官流程冒烟（出题→作答→收尾→token 记账）复核通过

**复测**：错误率 19.4% → 0%，吞吐 ×4.4，p95 64s → 9.2s。

## 4. 瓶颈分析

1. **LLM 上游延迟是 p95 的主导项**。单个 /api/query 在 Agent 不充分时串行执行
   「改写 + 检索 + 生成」最多 4 次 DeepSeek 调用，决定了 5~9s 的延迟基线；
   这不是服务端算力瓶颈，继续加并发额度收益有限。
2. **embedding CPU 是可测但可控的次因**。S2 中 worker 摄入（CPU 密集）仅抬高
   问答 p95 约 8.5%，得益于 `max_jobs=2` 的并发上限与 to_thread 隔离。
3. **LLM 信号量未成为瓶颈**：三轮压测未观察到 429，8 并发额度对当前负载充裕；
   DeepSeek 侧若收紧限额，`llm_gate` 的 1s/2s/4s 指数退避已就位。
4. 单 uvicorn 进程 + 默认线程池（40）足够覆盖 20 并发；更高并发应先加
   uvicorn workers 或上 gunicorn，而非放宽 LLM 信号量。

## 5. 附带发现（未改，供后续参考）

- **短主题词开考被拒**：exam/start 用单词级 topic（如 "RAG"）检索时余弦分低于
  阈值 0.65，返回 400「没有相关资料」。语义完整主题（如"RAG 系统的检索质量与
  混合检索"）得分 0.78+ 正常通过。建议前端在主题过短时提示用户补充描述。
- S1/S2 首轮的 `--tags` 方式会让无匹配任务的用户类报错退出码 1，压测脚本
  已改为按用户类名位置参数筛选（见 locustfile docstring）。

## 6. 复现命令

```bash
# 起栈（本地等效）：redis-server → arq worker → uvicorn
python -m arq app.worker.WorkerSettings          # backend/ 下
python -m uvicorn app.main:app --port 8000       # backend/ 下

pip install -r backend/requirements-dev.txt       # locust

# S1/S2（S2 在跑到 60s 时手动上传 20MB PDF）
locust -f backend/tests/load/locustfile.py --headless QueryUser \
       -u 20 -r 5 -t 3m --host http://127.0.0.1:8000 --csv out/s1

# S3（10 query + 5 exam，按 weight 2:1）
EXAM_AUDIT_FILE=out/exam_audit.json \
locust -f backend/tests/load/locustfile.py --headless QueryUser ExamUser \
       -u 15 -r 3 -t 3m --host http://127.0.0.1:8000 --csv out/s3
```
